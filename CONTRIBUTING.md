# Contributing

Keep the framework general and its explanations understandable to someone new to the method. Project-specific facts belong in examples or project documents. Change a shared instruction when an observed failure shows why the change is useful.

For tooling changes, run the checks in [technical setup](docs/technical-setup.md). For a schema change, update the validator, templates, examples, skills, and file-contract documentation together. For documentation changes, check local links and make sure commands still use the actual layout.

A useful contribution explains the problem, resulting behavior, verification, and practical limits. Tests should demonstrate meaningful invariants or failures rather than require a particular sentence or heading. Report unrun checks honestly.

Use fictional or sanitized examples. The repository's MIT license covers new contributions unless an alternative is explicitly agreed before inclusion.
