# Useful difficult cases

Try these with an assistant when changing a skill. Use a temporary copy of an example, and keep the failed output so you can compare the next attempt.

| Input or situation | Expected behavior |
|---|---|
| “Make onboarding better” with no users or outcome | Scope records uncertainty and asks the decision that matters; it does not invent survey findings |
| A document project with no programming language | Architecture describes people, documents, and handoffs without adding a web service |
| One small useful outcome | Decomposition writes one deliverable rather than inventing a quota of extra work |
| A developer-facing API contract | Criteria may state observable interface behavior; incidental library choices stay in the plan |
| A plan references an unknown AC | Validator rejects it; planning corrects the reference |
| A plan requires an unavailable system | Creation records the environment blocker and checks what it can independently |
| A command was proposed but not run | Summary and review record not_run; the criterion stays not_verified |
| A criterion changes after planning | Validator rejects the stale snapshot; planning revisits affected tasks |
| A plan changes after a passed review | Validator rejects the stale review digest; review must be performed again |
| Two projects share the same deliverable prefix | Their files remain separate because the caller names a project path |
| A reviewer finds a real failure | A non-passing verdict and matching work-list status are recorded with a concrete next step |

For each case, distinguish a successful file validation from a good decision. A perfectly formatted invented assumption is still a poor result.
